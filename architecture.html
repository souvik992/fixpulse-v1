System Overview

Page 2

FixPulseHQ is a multi-tenant SaaS bug tracking platform built on a single Node.js process (clustered to all CPU cores via PM2). The system follows a classical 3-tier architecture: browser client → Express API server → PostgreSQL database, augmented with Redis for horizontal-scaling concerns (presence and query caching) and a Worker Thread pool for CPU-intensive XLSX generation.

🖥 Frontend

Single-page React 18 app loaded via CDN UMD. Babel parses JSX at runtime. No build step needed at runtime — uses app.bundle.js from esbuild for production.

⚙️ Backend

Express.js REST API. Full security middleware chain. JWT-authenticated routes. RBAC permission gate on every sensitive operation. PM2 cluster for multi-core scaling.

🗄 Data

Neon-hosted PostgreSQL with a 20-connection pool. Redis for real-time presence (sorted sets) and query cache (30–60s TTL). 8 composite + partial indexes.

Frontend Architecture

Page 3

The frontend is a single-page application (SPA) built entirely in React 18 running inside a single HTML shell. There is no frontend framework router dependency — routing is handled by React state. Babel Standalone compiles JSX at runtime in development; esbuild produces app.bundle.js for production.

State Management

React Context (no Redux). Two global contexts:

AuthContext — holds JWT token, current user object, org payload. Persists in localStorage. Token is sent as Authorization: Bearer <token> on every API call.

OrgContext — holds org settings including plan code, data source config, and Apps Script URL.

Routing Strategy

No React Router. App checks bt_has_token=1 cookie to decide which shell to serve. The Express catch-all redirects unknown paths to index.html or app-shell.html. Pages are React state variables toggled by sidebar nav.

Build Pipeline

Development: Babel Standalone loaded from CDN parses JSX on the fly in the browser. No local build step. Hot reload via nodemon.

Production: npm run build:app runs esbuild, bundles public/app.js → public/app.bundle.js (IIFE format). Static assets served with maxAge: 1h and ETags.

API Communication

All API calls are plain fetch() with JSON. The base path is the same origin. Attachments are encoded as base64 data URLs inline in JSON. Large responses (bugs list) are paginated at 20 items per page.

↓

↓

↓

↓

↓

Password Security

bcryptjs with cost factor 10 (≈100ms hash time). Passwords never stored in plain text. Password reset uses a randomUUID() token stored in password_reset_tokens table with 1-hour expiry.

Database Schema

Page 5

PostgreSQL hosted on Neon (serverless, edge-cached). Connection managed by pg.Pool (max 20 connections, 30s idle timeout, 5s connection timeout). All tables are scoped by org_id for multi-tenancy.

Performance Indexes

Index NameType & Purpose
idx_bugs_org_projectComposite — accelerates WHERE org_id=X AND project_id=Y
idx_bugs_assigneePartial (non-null) — filter bugs by assignee
idx_bugs_statusComposite — status filters + stats queries
idx_bugs_created_atDESC — default sort order
idx_bugs_sheet_pushedPartial (IS NULL) — incremental sheet push
idx_activity_bug_idSingle — activity join on bug detail
idx_comments_bug_idSingle — comments join on bug detail

Multi-Tenancy

Every table except roles and permissions carries an org_id column. All API routes filter by req.user.orgId which comes from the JWT token, preventing any cross-org data access.

Organizations have isolated: users, projects, bugs, roles, settings, data sources, and billing orders.

Connection Pool

max: 20 — up to 20 concurrent DB connections per Node.js process. With PM2 cluster (N cores), total pool size = 20 × N connections. Size N's Neon plan accordingly.

idleTimeoutMillis: 30s — returns idle connections to pool.
connectionTimeoutMillis: 5s — fails fast if pool exhausted.

Pool error events are caught and logged — prevents Neon ECONNRESET from crashing the process.

Role-Based Access Control (RBAC)

Page 6

FixPulseHQ implements a flexible, two-layer RBAC system. Users can have organisation-level roles (global) and project-level roles (scoped). The system merges permissions from both layers for any given request context.

Permission Resolution Algorithm

1. Query user_roles JOIN role_permissions JOIN permissions where user_id=$1, org_id=$2, and project_id IS NULL OR project_id=$3.
2. If rows found → return merged Set of permission names.
3. If no user_roles rows at all → fall back to legacy users.role column → map to LEGACY_ROLE_PERMISSIONS.

Project-Level Scoping

A user can be a Viewer org-wide but a Developer on one specific project. The checkPermission middleware accepts a dynamic projectId resolver function — for bugs, it looks up the bug's project before checking permissions. The SQL query merges org-level + project-level permissions automatically.

Redis — Presence & Cache Layer

Page 7

Redis enables two features that require shared state across multiple Node.js processes: real-time user presence and query result caching. Both degrade gracefully to in-process fallbacks when REDIS_URL is not set.

Presence System (Sorted Sets)

Each org's online users are stored as a Redis Sorted Set:

Key: presence:{orgId}
Member: userId
Score: Date.now() (millisecond timestamp)

User data (name, avatar, color) is stored separately as a JSON string:
presence_data:{orgId}:{userId} with TTL = 60s

Client heartbeat (every 30s) → POST /api/presence/heartbeat
↓
Redis PIPELINE: ZADD presence:{orgId} now userId & SETEX presence_data:... 60s
↓
GET /api/presence → ZREMRANGEBYSCORE (prune >45s old) + ZRANGEBYSCORE + MGET data
↓
Returns array of online user objects — visible in PresenceBar UI

Tab close: navigator.sendBeacon posts token to POST /api/presence/offline → immediately removes from sorted set. Stale entries auto-expire via TTL and timestamp filtering.

Query Cache

Cache KeyTTLInvalidated by
members:{orgId}60sPOST/PUT/DELETE /api/members
stats:{orgId}:all30sBug create / update / delete
stats:{orgId}:{projectId}30sBug create / update in project

Cache hit: cache.get(key) → returns parsed JSON, skips DB entirely.
Cache miss: DB query runs → result stored with SETEX key TTL JSON.
Cache write failures are silently swallowed — Redis being down never breaks a request.

In-Process Fallback

When REDIS_URL is absent or Redis is unreachable:

  • Presence → falls back to Map<orgId, Map<userId, entry>> in memory (single-instance only)
  • Cache → all cache.get/set/del calls are no-ops; every request hits the DB

The server logs ℹ️ REDIS_URL not set — using in-process fallback at startup.

Redis Connection Config

maxRetriesPerRequest: 1 — fails fast, doesn't queue
enableOfflineQueue: false — drops commands when disconnected
connectTimeout: 5000ms — startup fail-fast
lazyConnect: true — explicit redis.connect() in boot sequence

Google Sheets via Apps Script

The app integrates with Google Sheets using a deployed Apps Script Web App as a serverless HTTP endpoint. No Google credentials are stored — the script is publicly deployed ("Anyone" access).

Two-way sheet integration

Direction A: DB → Sheet (Push)
↓
POST /api/sheet-push → pushToAppsScript()
↓
Query bugs WHERE sheet_pushed_at IS NULL (incremental)
↓
HTTPS POST { action: 'append', sheets: [...] } to Apps Script URL
↓
On success: UPDATE bugs SET sheet_pushed_at = NOW()
Direction B: Sheet → DB (Sync)
↓
googleSheetSync.js runs every 60 min (configurable)
↓
Downloads sheet (CSV export URL or XLSX) via HTTPS GET
↓
Upserts rows into bugs table (create or update by key)
Apps Script actions handled:
push_all — clear tab + write all rows
add_tab — create new sheet tab with headers only
append — append new rows only (incremental, no data loss)
SMTP Email (Nodemailer)

Nodemailer sends transactional emails for two events. The transporter is lazily initialised on first send and reused for all subsequent sends.

All sends are non-blocking — the API response is returned immediately and email delivery is a fire-and-forget .catch() chain. SMTP failures never break a request.

EventTrigger
Issue AssignmentPOST /api/bugs — when assigneeId is set. Sends assignee name, issue key, type, priority, description.
Password ResetPOST /api/auth/forgot-password. Sends a randomUUID() token link valid for 1 hour.
Razorpay Payment Gateway

Used for paid plan upgrades (Plus: ₹2,999/mo, Enterprise: ₹9,999/mo). Payment flow:

Admin clicks Upgrade → POST /api/billing/create-order
↓
razorpay.orders.create() → returns order_id. Stored in billing_orders table.
↓

↓
POST /api/billing/verify-payment
↓
HMAC-SHA256 signature verified: orderId|paymentId
↓
org.plan_code updated → new user limit applied immediately

Graceful Shutdown

SignalBehavior
SIGTERMStops accepting new connections. Waits for in-flight requests to complete. Exits cleanly. (Container stop / Kubernetes eviction)
SIGINTSame as SIGTERM. Triggered by Ctrl+C in terminal.
Timeout (15s)If requests don't drain in 15s, process.exit(1) is forced. .unref() ensures the timer doesn't prevent normal exit.

HTTP Tuning

server.keepAliveTimeout = 65_000ms — exceeds AWS ALB 60s idle timeout. Prevents 502 errors from keep-alive connection races.

server.headersTimeout = 70_000ms — must be > keepAliveTimeout. Prevents node from sending headers on a half-closed connection.

PM2 Configuration Highlights

instances: 'max' — PM2 detects CPU count at runtime
exec_mode: 'cluster' — Node cluster API, shared port
max_memory_restart: '512M' — auto-restart leaky workers
kill_timeout: 15000 — matches graceful shutdown window
autorestart: true + max_restarts: 10
merge_logs: true — consolidated log file
Zero-downtime reload: pm2 reload ecosystem.config.js
